# Customerssay 评价与 Sectionly B2B 接入方案

日期：2026-11-13（北京时间）。状态：已按用户确认的位置完成本地实现；两把开发密钥已单独获准创建并仅保存本机。真实业务写入、推送与部署仍按各自边界确认。

## 目标与范围

在现有 Hydrogen 2026.4.7 / React 18 网站上接入两个已安装应用，使用本站 React 界面与官方 Headless API，沿用英、日、德语言路由。保留现有零售价格、加购、Shopify 托管结账和 17TRACK 查询功能；不新增框架或假设未公开的 React 包可以安装。

第一阶段交付 B2B 在线询价，第二阶段交付商品评价。每阶段独立验收，不用“后台已安装”代替“网站已可用”。

## 已确认的页面位置

- 商品标题下、价格上仅增加一行平均评分和评价数量，可跳到评价区；不放大卡片。
- 完整评价区放在详情图之后、现有批发与定制之前；详情导航增加 Reviews 锚点。
- 首屏规格下的 Request a quote 直接打开现有询价弹窗；下方 Wholesale/OEM/ODM 入口共用同一弹窗，带入当前商品规格、数量和需求类型。
- 客户要求交付入口截图：评分入口和首屏询价入口/弹窗；截图标明本地预览，不以测试数据冒充真实评价或已接通状态。

## 官方契约与现状

- [B2B Headless 指南](https://docs.sectionly.ai/zh/b2b/headless)、[完整接口文档](https://b2b.sectionly.ai/headless/docs)：使用独立 B2B 密钥，读取 `/form-config`、`/b2b-products`，向 `/inquiry` 提交 JSON。每个访客使用随机标识，每个询价使用独立幂等键；结果为询价保存成功，草稿订单异步创建。
- [Reviews Headless 指南](https://docs.sectionly.ai/zh/reviews/headless)、[完整接口文档](https://app-next.customerssay.ai/headless/docs)：读取评论、评分汇总和组件设置；评论及媒体上传使用 FormData。成功提交可能仍需审核。评论提交没有 B2B 同样的幂等契约，不在超时后自动重复写入。
- 上述中文指南正文已于本轮重新读取；具体请求/响应字段、错误码与表单设置，在实施前继续按完整接口契约逐项核对，不能猜测。
- 当前 `ProductBusiness.jsx` 只生成邮件草稿。商品路由尚未加载真实评价；`SiteSeo.jsx` 已有 Product 结构化数据。当前变体查询不足以保证获得所有 SKU，多规格询价必须另做分页读取。

## 一、B2B 在线询价

1. 复用现有询价区域和原生弹窗。打开时带入真实商品、当前 SKU 和数量；补充姓名、邮箱，按应用配置渲染必填项、MOQ 和可询价状态。首版以当前商品的一个或多个规格为询价范围；不新增跨商品询价购物车。
2. 按需分页读取完整规格，避免首屏加载全部规格。后台规则决定可选规格与最低数量；由 Shopify 读回的商品/变体信息校验归属，不接受浏览器价格作为报价依据。
3. Wholesale、OEM、ODM 类型保留，定制内容按官方允许的自定义字段或备注提交；字段映射先核对，不能假设任意字段均受支持。
4. 增加本站服务端提交接口，固定第三方目标地址并限制请求大小，验证来源、请求格式与字段，采取 CSRF 与滥用保护。服务端密钥只在服务器使用；可信客户端 IP 的来源按 Oxygen 实际运行环境核对，不直接信任任意转发头。
5. 通过现有签名会话保存访客标识。客户端持有本次操作 ID；网络结果不确定时，保持相同幂等键和完全相同的请求内容重试。内容变更后创建新操作，阻止重复点击与重复草稿订单。若支持跨刷新恢复，不将邮箱、需求等个人信息长期保存到浏览器。
6. 页面只在收到成功结果后显示询价编号，并说明后续报价流程。将“询价已收到”与“草稿订单已创建”分别验收；失败时保留用户输入，提供重试或原有邮件联系入口，不能显示虚假成功。

## 二、商品评价

1. 在商品页增加真实评分摘要、已发布评价列表、分页与写评价表单；支持官方表单要求的评分、昵称、邮箱和正文。图片上传在媒体契约、格式、大小和数量限制确认后接入；视频、店铺评价与商品问答不纳入首期。
2. 服务端读取首屏已发布评价与评分，超时/故障时显示暂不可用，不将读取失败伪装成零评价。仅公开评论可以按商品和分页短时缓存；个人信息、写入结果和身份相关数据不进入公共缓存。
3. 复用本站服务端提交方式，校验来源、表单设置、评分范围、媒体限制及商品归属，保护邮箱等个人信息。提交后明确提示审核状态；没有可信购买身份时不授予已验证购买标记。
4. 客户端切换商品、规格或语言时保证评论属于正确商品；同商品不同规格沿用商品级评价，不重复制造评价记录。
5. 在现有 Product JSON-LD 中合并真实评分/评价信息，不额外生成冲突的 Product 节点。无公开评价时不输出虚假评分；媒体和评论文本按安全方式渲染。

## 配置与授权边界

- 首先使用受控的本地接口替身验证真实边界条件，测试数据不出现在正式店面。没有有效配置时显示不可用或保留联系入口，不伪装完成接通。
- 真实联调前单独说明并请求：为本店创建两个应用各自的接入密钥、所需最小权限/有效期、实际允许域名，以及只新增所需本地环境项的范围。没有授权不读取/创建/替换密钥，不修改 `.env`、生产配置或 CI/CD；不轮换其他现有凭据。
- 真实测试询价可能产生草稿订单和通知；真实测试评价可能进入审核。执行前列明测试身份、数量、触发的通知及后台写入范围，取得针对该范围的批准。不发送批量邀评，不自动选择付费套餐，不删除测试记录。
- 本地开发与代码验证不等于生产接通。每次 push 与生产发布分别准备审查范围并取得批准。

## 验收与顺序

1. 用户确认本方案后，先实现并验证 B2B，再实现并验证评价。保留旧功能回归；最终分别形成可审查提交。
2. 测试覆盖：MOQ/必填规则、变体归属、重复提交、超时与幂等重试、审核状态、评价读取失败、媒体限制、恶意输入、跨商品导航和密钥隔离。
3. 执行 `npm run lint`、`node --test tests/*.test.mjs`、`npm run codegen`、`npm run build`、`node scripts/check-collection-filters.mjs`、`node scripts/audit-source-exposure.mjs --built`；商品页内容变更同时核对 `tests/sitemaps.test.mjs` 及受影响 sitemap。
4. 通过专用 Chrome for Testing 验证桌面/手机、英日德文案、键盘/弹窗焦点、表单失败保留和成功状态；回归 SKU/图库、数量、购物车及结账入口，不完成付款。按当前浏览器规则复用专用资料，不接管日常浏览器。
5. 获准的真实联调分别读回应用中的询价/草稿订单、待审评价，并核对首屏 HTML 与结构化数据。缺少真实凭据或写入批准时明确保留该验收缺口，不声称端到端完成。

方案确认只覆盖上述本地开发范围；不自动批准密钥配置、真实业务写入、推送或公开发布。
